The RAG Retrieval Boundary

Three questions you asked at the end of Lesson 06, answered for morning review. The through-line: a real vector database makes retrieval smarter, not safer. Every retrieved chunk is still untrusted data, and the boundary is still a deterministic gate in your code.1

Q1 · How a real vector DB + embeddings slots into Step 1 — without changing the security story

In the lesson, retrieve() was a dictionary keyword match. In production you swap that one function for an embedding model + vector store. Nothing else in the pipeline changes — and, crucially, neither does the trust model.

Offline, once (ingest):

for doc in corpus:
    vec = embed(doc.text)                 # embedding model → a vector
    index.upsert(id=doc.id, vector=vec,
                 text=doc.text,
                 metadata={"owner": doc.owner, "acl": doc.acl})   # ← keep this

Per query (retrieve) — the only line that changed from Step 1:

qvec = embed(user_q)                       # embed the QUESTION
hits = index.query(qvec, top_k=3,
                   filter={"acl": current_user.groups})   # ← access control HERE, in code
context = "\n\n".join(h.text for h in hits)
# …then the SAME augment → generate → OUTPUT GATE as the lesson.

Why the security story is identical

An embedding is a similarity function, not a sanitizer. Retrieval finds text that's semantically close to the question — it never inspects that text for instructions. So a poisoned chunk that ranks well is retrieved and pasted exactly like the dictionary version. The retrieved chunk is untrusted before embeddings and untrusted after. Fancier retriever, same indirect injection surface.

But embeddings add three new wrinkles (bank these for the capstone):

New wrinkle What it means for you
Retrieval hijacking An attacker can craft a chunk stuffed with high-salience terms so it ranks top-k for many queries — getting their payload retrieved far more often than a naive keyword match would.
top-k = more untrusted text Returning the 3–10 nearest chunks means 3–10 independent injection chances per answer, not one. Blast radius scales with k.
Access control moves to query-time The vector store holds everyone's data in one index. If you don't filter by the user's permissions at query time (that filter= line), retrieval leaks across tenants — a data breach with no injection required.

Q2 · How RAG poisoning differs from tool-result poisoning

Same threat class (untrusted text → model's next decision), but the timing and attacker's access differ, and that changes how you defend.

Tool-result poisoning (L05) RAG / index poisoning (L06)
When planted At call time — the payload lives in whatever the tool reads right now (a live web page, an API response, a file on disk). Ahead of time — the payload was written into the corpus earlier and sits dormant until a query happens to retrieve it. (EchoLeak: the email arrived days before the victim asked anything.)
Attacker needs Control of a source the tool fetches (a page you scrape, an inbox you read). Write access to the index — or to anything that feeds the index (a shared doc, a ticket, a crawled site).
Trigger Deterministic-ish: fires when the agent calls that tool in the loop. Probabilistic: fires only when a query is semantically close enough to retrieve the poisoned chunk — which is why attackers do retrieval hijacking (Q1).
Blast radius This session, this agent. Every user whose query retrieves it, until the chunk is found and purged. One write, many victims.
Extra defense it demands Treat the result as untrusted; gate the next action. All of that plus control write access to the corpus and track chunk provenance, so you can trust-rank and purge sources.

The one-line difference

Tool-result poisoning is an attack on what the model reads now; RAG poisoning is an attack on what you stored earlier. So RAG adds a defense the loop didn't need: secure the write path into the index, not just the read path out of it.

Q3 · Threat-modeling the whole retrieval pipeline — "who can write to the index?"

Same method as Card 03, aimed at the pipeline instead of the loop. Walk every stage and ask the boundary question. The one most teams skip is the very first.

  WRITERS ──▶ [ INGEST ] ──▶ [ INDEX ] ──▶ [ RETRIEVE ] ──▶ [ AUGMENT ] ──▶ [ MODEL ] ──▶ [ OUTPUT ]
  who can        chunk +       stored,       top-k by         delimit as     generates      GATE:
  add text?      embed         multi-tenant  similarity       untrusted      (persuadable)  no exfil
     ▲            ▲             ▲             + ACL filter                                   channel
  the real    poisoned      cross-tenant   leak if no                                    the EchoLeak
  front door  chunk lands   leak risk      filter                                        wall
  1. INGEST — enumerate the writers (the question you asked). List everyone and everything that can put text into the corpus: employees, end-users, uploaded files, inbound email, support tickets, crawled web pages, third-party API syncs. Each writer is an injection author. Classify the corpus: curated (only trusted authors write) vs. open (any user or external content flows in). EchoLeak was an open corpus — an outside email got indexed. Open corpora are where poisoning lives.
  2. INDEX — integrity & tenancy. Is the store multi-tenant? Every chunk needs an owner/acl tag at write time (Q1) or you can't filter it at read time. Can a writer overwrite or delete others' chunks? Log who wrote what — that's your provenance trail for purging a bad source later.
  3. RETRIEVE — enforce access control here, in code. The retriever must return only chunks this user is allowed to see (the filter= line). This is authz, and like every authz decision in this course it lives in your code, never the model's judgement (enforce authz in code). Skip it and you get cross-tenant leakage with no injection needed.
  4. AUGMENT — delimit. Wrap retrieved chunks in <untrusted_context>. Raises the cost of injection; still probabilistic, not a wall (delimiting).
  5. MODEL — assume it loses. A persuasive enough chunk will win. Don't spend your budget here; spend it on the two boundaries around it (retrieve + output).
  6. OUTPUT — the wall (this is where EchoLeak broke). A deterministic gate on the way out: strip/deny outbound URLs, never auto-render model output as live HTML, don't let a reply become an exfiltration channel. Persuasion is expected; the breach is a missing output gate.2

⚠ The two RAG-specific boundaries the agent loop didn't have

1. The write path (INGEST). "Who can write to the index?" is the new front door — a curated corpus removes a whole class of poisoning that a locked-down loop never faced. 2. Retrieval access control (RETRIEVE). One shared index over many tenants means a missing permission filter is a silent data breach, entirely separate from injection.

The one rule (RAG edition)

Threat-modeling a retrieval pipeline = secure the write path in (who can poison the corpus), the read path out (whose data can this query reach), and the output path (can a reply exfiltrate) — with a deterministic check on each. The model in the middle is the one component you assume is already compromised.
