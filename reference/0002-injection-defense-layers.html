Injection Defense — the Four Layers

A quick-reference for hardening any LLM feature against prompt injection. Layers 1–2 reduce probability; layers 3–4 are the real boundary. Defense in depth: use all four.1

# Layer What it does Boundary?
1 Structured input / delimiting
Mark untrusted text as DATA, not COMMANDS: explicit sections (USER_DATA: vs SYSTEM_INSTRUCTIONS:), fenced delimiters.		 Raises the model's cost to obey injected instructions. No — probabilistic
2 Input & output validation
Deterministically screen inputs for injection/obfuscation, and screen outputs for leakage, secrets, unsafe markup/links.		 Catches known-bad patterns before and after the model. Partial — bypassable
3 Least privilege on tools/actions
Read-only creds, scoped APIs, validate every tool call against the user's actual permissions. Assume the model will be tricked.		 Caps the blast radius — injection can't exceed granted rights. Yes — deterministic
4 Human-in-the-loop
Require explicit human approval before any destructive or high-privilege action executes.		 Final gate on irreversible actions. Yes — deterministic

The one rule

Treat model output as untrusted input. Never let model output trigger a privileged action without a deterministic gate in your own code — least-privilege scope (Layer 3) and/or human approval (Layer 4). Everything inside the prompt is persuasion; only code outside the model is a boundary.

⚠ Trap

A "guardrail LLM" that screens for attacks is itself an LLM and is itself injectable. It's a Layer-2 aid, never a replacement for Layers 3–4.1
