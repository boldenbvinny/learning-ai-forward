The Agent Trust Boundary

RAG, memory, and threat-modeling an agent — all one idea. Every source that feeds the context window is untrusted data; the only boundary that holds is a deterministic gate in your own code, downstream of the model.1

The data-flow — memorize this shape

Draw any agent this way. Everything on the left flows into one flat context window; the model turns it into a tool call; only your gate decides if it acts.

  user input ───┐
  RAG docs ─────┤                                                  ┌── attacker can plant text
  memory files ─┼──▶ [ MODEL / context window ] ──▶ tool_use ──▶ [ YOUR GATE ] ──▶ action
  tool results ─┘            ▲                        (request)    (deterministic)    │
                             └──────────── tool_result (UNTRUSTED) ◀─────────────────┘
                                            the loop closes the circuit

Security spine

Every arrow into the model box is a potential indirect injection vector — not just the user. A poisoned RAG chunk, a poisoned memory file, or a poisoned tool result is the same threat class you met in Lesson 05: attacker-controllable text becoming the input to the model's next privileged decision.

RAG & memory — where they plug in

Mechanism Gap it fills Where in the loop Its danger
RAG Stateless → the model doesn't know your data. Retrieve relevant docs, inject as context. Pre-loop (prepend top-k) or as a search tool inside the loop. Anyone who can write to the corpus (a ticket, a wiki, a scraped page) plants instructions the model will retrieve.
Memory Cross-session statelessness. A tool (memory_20250818) that writes notes to a /memories dir that persist. A tool call inside the loop whose "action" is write a note to my future self. Worse — it persists. One injection writes a poisoned note that replays into every future session.

⚠ Two memory-specific traps

1. Never store secrets in memory — they replay verbatim into future context. 2. Validate every model-supplied path — the memory tool takes file paths from the model; reject .. traversal and symlinks. The model's input is attacker-controlled, so its paths are too.

Threat-modeling the loop — the method

It's a trust-boundary exercise you already know from services. Walk it with OWASP GenAI as the checklist:1

  1. Enumerate the tools = enumerate the blast radius. For each tool, ask: worst case if the model calls it with attacker-chosen arguments? A granular delete_file(path) you can gate; an open-ended bash(cmd) you cannot. (Excessive agency, LLM06.)
  2. List every untrusted-data source. User turns, RAG corpus, memory, and every tool result. Rank by attacker-controllability: can they edit the wiki? plant a ticket? poison a scraped page? (Indirect injection, LLM01.)
  3. The loop amplifies. A one-shot call gives an attacker one attempt; an agent loop gives N iterations plus a persistence surface (memory). More autonomy = more surface.
  4. Confirm a gate sits on every path from an untrusted source to a privileged action — least privilege scope and/or human-in-the-loop, firing on every iteration, behind a hard loop cap.

The one rule

Threat-modeling an agent = finding every path from an untrusted-data source to a privileged action, and confirming a deterministic gate sits on each one. RAG docs, memory files, and tool results are all untrusted data — the gate is always code the attacker can't argue out of (enforce authz in code).

Aside — the SDK tool-runner vs. the hand-written loop

The SDK's tool_runner writes the loop for you (in Python, @beta_tool + client.beta.messages.tool_runner). It does not remove the gate — you either gate inside the tool function or between iterations. We hand-wrote the loop in Lesson 05 for one reason: it puts the gate visibly between the model's request and execution, so the boundary is where you can see and maintain it. Graduate to the runner in production; just keep the gate somewhere you won't forget it.
