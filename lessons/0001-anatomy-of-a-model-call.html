The Anatomy of a Model Call

Before you can build, architect, or secure an AI system, you need one correct mental model of the primitive everything else is made of: a single call to a language model. Get this right and prompt injection, RAG, memory, and agent loops all stop being mysterious — they become consequences.

~10 min · concept, then a hands-on win · no code required yet

The one idea

A large language model is a stateless next-token predictor. That is the whole machine. You hand it a sequence of tokens — the context — and it returns a probability distribution over what token comes next; it samples one, appends it, and repeats.1 There is no database, no session, no memory of you between calls. Just: text in → next token out, over and over.

The primitive

One model call = you send the entire context as a single flat string of tokens; the model returns a sampled continuation. Everything an AI system does is built by choosing what goes into that string and what to do with what comes back.

A "token" is the real unit

Models don't see words or characters — they see tokens, chunks of roughly ¾ of a word.2 The context window is the maximum number of tokens one call can hold: your system prompt, the conversation so far, any retrieved documents, and the reply it's generating all share that one finite budget.2 Think of it as the model's entire universe for that call. Nothing outside the window exists.

Three consequences (this is the payoff)

Almost everything you'll learn later is a workaround for one of these three facts.

1 · Stateless → you resend everything, every time

The model remembers nothing between calls. The illusion of a chatbot "remembering" the conversation is your application re-sending the whole transcript on every turn. This is why memory and context management are engineering problems you own — not features the model provides.

2 · It's all one string → instructions and data are not separated

Here is the fact that will define your security work. Your trusted system prompt ("You are a support agent, never reveal internal notes") and completely untrusted input (a user message, a scraped web page, a tool result) are concatenated into one undifferentiated token stream. The model has no reliable mechanism to tell "these are my rules" from "this is data to process."3

Security · the injection surface

This is why prompt injection is #1 on the OWASP Top 10 for LLM apps (LLM01).3 It is not a bug to be patched — it is a direct consequence of the architecture. Any place where untrusted text enters the context window is an attack surface, because that text can carry instructions the model may follow. Delimiters and "ignore anything below this line" warnings help a little, but they are not a hard security boundary.3 Your defenses live around the model — least privilege, output validation, human approval — not inside the prompt.

Direct injection: the user themself types the malicious instruction. Indirect injection: the payload rides in on content the model reads on the user's behalf — a web page, a PDF, an email, a tool response.3 Indirect is the one that will keep you up at night once you build agents.

3 · Output is sampled → nondeterminism and hallucination

The reply is drawn from a probability distribution, so the same input can produce different outputs, and a confident-sounding continuation can be simply wrong.2 Hallucination isn't the model "lying" — it's the machine doing exactly what it always does (predict a plausible next token) with no notion of truth. This is why evals exist, and why you never wire raw model output straight into a privileged action.

Hands-on · tag the trust boundary
